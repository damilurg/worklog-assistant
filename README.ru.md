# GitLab → Jira Worklog Assistant

Self-hosted монорепозиторий на TypeScript: существующий CLI для GitLab/Jira, Angular-интерфейс активности только на английском и граф разработки. CLI хранит исходные записи в PostgreSQL, сервис графа — их проекции в MongoDB.

Worklogs из Jira читаются, но новые автоматически не записываются. Существующие CSV/JSON-отчёты CLI распределяют заданный рабочий день; фактические итоги интерфейса используют импортированные секунды worklogs Jira. Для будущей записи в Jira требуется подтверждение пользователя.

## Что реализовано

- Существующая синхронизация коммитов, MR и review-комментариев нескольких GitLab, задач/worklogs Jira, покрытие диапазонов, отчёты и экспорты CLI.
- Angular-граф связей: ссылки на источники, поиск, фильтры узлов, масштаб и фокус на один/два уровня.
- Активность по дням/часам, события разработки/ревью, реальные слияния MR и записанное в Jira время.
- Журнал источников: ID строк, даты, исходные секунды, фильтры дня/источника, страницы и JSON-экспорт.
- Кешированные проекции графа в MongoDB; изменения дат и фильтров не вызывают внешние API.
- Отдельные команды live/demo, серверные токены и локальный Fastify API.

Автоматическая запись в Jira, импорт деплоев, исправление корректности импортера и изменение алгоритма распределения CLI остаются следующими задачами.

## Требования

- Node.js 24 или новее.
- pnpm 11.25.0, закреплённый в `packageManager`.
- PostgreSQL для реальных данных CLI.
- Docker с Compose v2 и поддержкой `--wait` для автоматического запуска локальной MongoDB либо существующая MongoDB с ручным запуском API.
- Деморежиму не нужны базы и токены сервисов.

## Установка и запуск

### Первый локальный запуск

Настройте `.env` с существующими параметрами GitLab/Jira. Уже настроенный файл не заменяйте.

```bash
cp .env.example .env
pnpm install
pnpm build
docker compose up -d postgres
pnpm --filter @worklog-assistant/db exec drizzle-kit push
pnpm graph
```

В PowerShell используйте `Copy-Item .env.example .env` вместо `cp`. Пользователи существующего CLI сохраняют `.env` и данные PostgreSQL; для графа новая миграция PostgreSQL не требуется.

Откройте **http://localhost:3000**. `pnpm graph` собирает монорепу, запускает локальную MongoDB, ждёт её готовности и поднимает API/UI. При старте обращений к GitLab/Jira нет: первый некешированный диапазон строится из уже сохранённых данных PostgreSQL. Кнопка **Sync workspace** запускает CLI за выбранные даты и обновляет MongoDB.

### Команды live и demo

```bash
pnpm graph        # Существующие данные CLI + граф MongoDB; без подстановки демоданных
pnpm graph:demo   # Только примеры; без баз и обращений к сервисам
pnpm graph:dev    # Angular на 4200; API должен работать на 3000
```

Для существующей MongoDB задайте `MONGODB_URI` и запустите API без локального контейнера:

```bash
pnpm build
node apps/api/dist/index.js
```

Для полного локального Compose-стека вместо API на локальном Node выполните `docker compose up -d --build` после создания схемы PostgreSQL. Compose передаёт `GITLAB_INSTANCES`, `JIRA_AUTH_MODE` и существующие фильтры авторов. Порты API и MongoDB опубликованы только на loopback.

## Поток данных и синхронизация

| Действие / компонент                                 | Читает                                          | Записывает / поведение                                                             |
| ---------------------------------------------------- | ----------------------------------------------- | ---------------------------------------------------------------------------------- |
| Существующий CLI sync                                | GitLab/Jira и покрытие синхронизации            | Исходные записи и покрытие в PostgreSQL                                            |
| Кешированный диапазон графа                          | MongoDB                                         | Возвращает проекцию; без запросов к PostgreSQL и сервисам                          |
| Первый некешированный диапазон                       | Существующие записи PostgreSQL                  | Строит одну проекцию в MongoDB; без запросов к GitLab/Jira                         |
| **Sync workspace**                                   | Существующий CLI и PostgreSQL                   | Обновляет выбранную проекцию MongoDB и сбрасывает остальные кешированные диапазоны |
| Фильтры дня/источника, фокус графа, страницы журнала | Загруженные данные браузера                     | Без серверных запросов и запросов к сервисам                                       |
| Изменение дат / **Apply dates**                      | Кеш MongoDB либо одна новая проекция PostgreSQL | Автоматически не синхронизирует внешние сервисы                                    |

Граф использует серверный `.env` CLI; токены в браузер не передаются. Одновременные чтения одного диапазона используют общий ожидающий запрос. Коллекция `worklog_graph.graph_snapshots` хранит атомарные документы с ключом из дат и лимита строк: граф, сводку активности и журнал источников. Ошибка чтения источника не заменяет существующий снимок.

CLI сохраняет инкрементальное покрытие и best-effort поведение. Покрытые диапазоны «источник/дата» пропускаются; ошибки допускают повторный запуск, предупреждения попадают в серверные логи. Для полной перезагрузки используйте существующий `pnpm sync --from ... --to ... --force`, затем **Sync workspace** для обновления проекций. Отдельный запуск CLI автоматически не сбрасывает уже кешированный диапазон графа.

## Даты, фильтры и деморежим

- UI и API по умолчанию показывают вчера–сегодня в UTC. Успешно загруженный диапазон указан явно.
- Даты применяются автоматически; **Apply dates** повторно загружает выбранный диапазон. Старый ответ не перезаписывает более новый выбор.
- Некорректные даты и ошибки API отображаются явно; предыдущие записи и демоданные не подменяют неудавшийся ответ live API.
- Выбор дня/источника фильтрует журнал локально. На странице 20 строк; JSON включает все подходящие строки загруженного среза, а не только текущую страницу.
- `graph:demo` использует фиксированный набор за **2026-10-08–2026-10-14**, применяет те же даты/лимиты и возвращает пустой результат вне этого периода. Базы и внешние сервисы не вызываются.

## Активность и происхождение расчётов

| Метрика               | Источник / формула                                                   |
| --------------------- | -------------------------------------------------------------------- |
| События по дням/часам | Сохранённые строки `activity_events`, сгруппированные по времени UTC |
| Разработка            | `activity_events.type = commit`                                      |
| Ревью                 | `activity_events.type = merge_request_reviewed`                      |
| Интеграция            | MR с реальным `merged_at` внутри выбранного периода                  |
| Записанные часы       | `SUM(jira_worklogs.duration_seconds) / 3600`                         |

Часовые столбцы считают события, а не отработанные часы. Продолжительность worklog относится к UTC-дате его начала и не распределяется по предполагаемым рабочим часам. Выводятся только даты с исходными строками.

Распределение планировщика, сгенерированные `worklog_entries`, нормализация на восемь часов и предположения о длительности работы не входят в фактические итоги. Импортированные значения Jira — проверяемые сохранённые записи, а не доказательство отработанных часов. Дубли и ошибки импортера остаются видимыми: интерфейс не исправляет и не удаляет их скрыто.

**Source ledger** показывает ID исходных строк, таблицы, время, типы, ключи задач и секунды. **Export source JSON** включает отфильтрованные строки, загруженный диапазон, UTC, выбранные фильтры, признак усечения и сумму записанных секунд. Формула за весь период отделена от фильтров журнала. Этот экспорт не вызывает распределитель времени отчётов CLI.

Слияния MR означают интеграцию, а не деплой. Для поставки нужны реальные записи деплоев из будущего расширения CLI. Принадлежность коммита MR не отображается: существующее хранилище её не содержит. Авторы коммитов GitLab и worklogs Jira имеют отдельные идентификаторы.

## API и ограничения хранилища

| Endpoint                                                 | Поведение                                                        |
| -------------------------------------------------------- | ---------------------------------------------------------------- |
| `GET /health`                                            | Состояние процесса и режим live/demo; не гарантия готовности баз |
| `GET /api/graph?from=YYYY-MM-DD&to=YYYY-MM-DD&limit=100` | Кешированный граф MongoDB либо первая проекция                   |
| `POST /api/sync` с теми же query-параметрами             | Существующий CLI sync и обновление MongoDB                       |

По умолчанию загружается до 100 строк каждого источника, `limit` — от 1 до 500. Усечение указано явно; итоги относятся к загруженному срезу, а не к невидимым записям. Даты включают целые календарные дни UTC. Проекция читает PostgreSQL в read-only repeatable-read транзакции.

Снимки MongoDB — ограниченные одиночные документы с лимитом 16 MiB. Отдельные индексированные коллекции узлов/связей, серверная пагинация, деплои и аудит импортера/отчётов — будущие улучшения. Приложение рассчитано на локальную работу одного пользователя: API по умолчанию слушает localhost и отклоняет нелокальные Host и cross-origin запросы браузера.

## CLI

После `pnpm build` используйте короткие команды из корня репозитория:

```bash
pnpm gitlab                         # GitLab за вчера
pnpm jira                           # Jira за вчера
pnpm sync                           # GitLab + Jira за вчера
pnpm sync --period half-year        # GitLab + Jira за полгода
pnpm standup                        # стендап за вчера
pnpm standup --date 2026-09-29      # стендап за дату
pnpm report                         # синхронизировать всё и создать worklogs.csv за вчера
pnpm report --period half-year      # синхронизировать полгода и создать worklogs.csv
pnpm report:json                    # синхронизировать всё и создать worklogs.json за вчера
pnpm finish                         # завершить сегодня: синк, CSV, JSON и стендап
pnpm get:report                     # завершить сегодня: только CSV и JSON
pnpm get:standup                    # завершить сегодня: только стендап
pnpm activity --from 2026-09-01
pnpm day 2026-09-29
```

Все флаги диапазона передаются в CLI. Перед построением отчёта выполняется синхронизация GitLab и Jira, которая обновляет нормализованную activity. Сгенерированные `worklogs.csv` и `worklogs.json` исключены из Git.

В конце рабочего дня запускайте `pnpm finish` без дат. Команда берёт сегодняшнюю дату в `TIMEZONE`, один раз синхронизирует оба источника, создаёт готовые к загрузке `worklogs.csv` и `worklogs.json`, а также сохраняет и печатает `standup.md`. Повторный запуск использует покрытие синхронизации; `pnpm finish --force` нужен только для полного обновления.

Заголовки стендапа всегда содержат точную дату и, когда применимо, подписи «Сегодня», «Завтра» и «Вчера».

Успешно обработанные пары «источник/дата» сохраняются в `sync_coverage` вместе с безопасным отпечатком конфигурации без токенов. Повтор той же команды пропускает покрытые даты без обращений к API, а пробелы объединяются в минимальные непрерывные интервалы. Изменение экземпляров, проектов, авторов или настроек Jira автоматически создаёт новую область покрытия. Используйте `--force`, только когда дату действительно нужно загрузить заново:

```bash
pnpm sync --from 2026-09-01 --to 2026-09-30 --force
pnpm report --from 2026-09-01 --to 2026-09-30 --force
```

GitLab повторяет сетевые ошибки, rate limit и временные ошибки сервера не более трёх раз с экспоненциальной задержкой. При ошибках авторизации, прав или отсутствии ресурса выполнение прекращается сразу. Неудачный диапазон никогда не отмечается обработанным.

В объединённых командах синхронизации и экспорта оба источника работают в режиме best-effort: если GitLab или Jira недоступны, команда выводит отдельное предупреждение для источника и продолжает работу с данными, уже сохранёнными в PostgreSQL. Неудачный диапазон не отмечается синхронизированным и будет повторён при следующем запуске. Отдельные команды `pnpm gitlab` и `pnpm jira` по-прежнему завершаются с ошибкой, чтобы мониторинг не пропустил сбой.

В комментарии отчёта используется название задачи Jira, выводятся не более двух уникальных событий GitLab, а остаток сворачивается в счётчик.

Полный собранный CLI также доступен:

```bash
# GitLab + Jira за вчера (по умолчанию)
node apps/cli/dist/index.js sync
# Готовые периоды истории, заканчивающиеся вчера
node apps/cli/dist/index.js sync --period week
node apps/cli/dist/index.js sync --period month
node apps/cli/dist/index.js sync --period half-year
node apps/cli/dist/index.js sync --period year
# Явный период для общей или отдельной синхронизации
node apps/cli/dist/index.js sync --from 2026-09-01 --to 2026-09-30
node apps/cli/dist/index.js gitlab sync --from 2026-09-01 --to 2026-09-30
node apps/cli/dist/index.js jira sync --from 2026-09-01 --to 2026-09-30
node apps/cli/dist/index.js activity --from 2026-09-01 --to 2026-09-30
node apps/cli/dist/index.js day 2026-09-30
node apps/cli/dist/index.js export --from 2026-09-01 --to 2026-09-30 --format csv > worklogs.csv
# Дополнительный структурированный формат
node apps/cli/dist/index.js export --from 2026-09-01 --to 2026-09-30 --format json
node apps/cli/dist/index.js report
node apps/cli/dist/index.js report --date 2026-09-29
```

Синхронизация и экспорт по умолчанию работают за вчера. Явные даты `--from/--to` имеют приоритет над `--period`. Отчёт также по умолчанию строится за вчера. Полный список команд: `node apps/cli/dist/index.js --help`.

### Ежедневный запуск по расписанию

Запускайте `node apps/cli/dist/index.js sync` один раз утром. В Windows Task Scheduler укажите `node` как программу, абсолютный путь `apps/cli/dist/index.js sync` как аргументы, а корень репозитория — в поле **Start in**. Для Linux/macOS пример запуска по будням:

```cron
0 9 * * 1-5 cd /path/to/worklog-assistant && node apps/cli/dist/index.js sync
```

## Переменные окружения

| Переменная             | Обязательна   | Назначение                                                                                            |
| ---------------------- | ------------- | ----------------------------------------------------------------------------------------------------- |
| `DATABASE_URL`         | Да            | Строка подключения к PostgreSQL.                                                                      |
| `GITLAB_INSTANCES`     | Для GitLab    | JSON-массив объектов `{ url, token, projectIds }`. Токену нужны права `read_api` и `read_repository`. |
| `GITLAB_AUTHOR_EMAILS` | Рекомендуется | Email авторов коммитов через запятую.                                                                 |
| `GITLAB_AUTHOR_NAMES`  | Рекомендуется | Имена авторов GitLab/коммитов через запятую.                                                          |
| `JIRA_URL`             | Для Jira      | URL сайта Jira.                                                                                       |
| `JIRA_EMAIL`           | Для Jira      | Email учётной записи Jira.                                                                            |
| `JIRA_TOKEN`           | Для Jira      | API-токен Jira.                                                                                       |
| `JIRA_AUTH_MODE`       | Нет           | `cloud` для Basic/API v3 или `data-center` для Bearer PAT/API v2. По умолчанию `cloud`.               |
| `WORKDAY_HOURS`        | Нет           | Длина рабочего дня, по умолчанию `8`.                                                                 |
| `TIMEZONE`             | Нет           | Часовой пояс IANA, по умолчанию `Asia/Bishkek`.                                                       |
| `MONGODB_URI`          | Нет           | Адрес MongoDB графа; по умолчанию `mongodb://127.0.0.1:27017`.                                        |
| `MONGODB_DATABASE`     | Нет           | База графа; по умолчанию `worklog_graph`.                                                             |
| `PORT`                 | Нет           | Порт локального API/UI; по умолчанию `3000`.                                                          |

`TIMEZONE` применяется в соответствующих операциях CLI; границы дат и графики интерфейса сейчас используют UTC. `WORKDAY_HOURS` влияет на планирование CLI, но не на фактические итоги времени в интерфейсе. Токены остаются на сервере; отдельный ключ в браузере не нужен.

Не добавляйте `.env` в Git: файл намеренно исключён.

## Разработка и проверки

| Путь              | Ответственность                                                 |
| ----------------- | --------------------------------------------------------------- |
| `apps/cli`        | Существующая синхронизация и отчёты                             |
| `apps/api`        | Fastify, проекция PostgreSQL, кеш MongoDB, агрегация активности |
| `apps/web`        | Angular UI и английские тексты в `src/i18n/en.ts`               |
| `packages/shared` | Контракты графа/активности и демонаборы                         |
| `packages/db`     | Существующая схема PostgreSQL/Drizzle                           |

```bash
pnpm test
pnpm lint
pnpm build
```

Автоматические тесты проверяют агрегацию без распределения рабочего дня, границы UTC, происхождение строк, кеш MongoDB с мокированной коллекцией, локальный API, даты деморежима и защиту от параллельных синков. Проверки Chromium покрывают автоматические даты, пустые периоды, страницы по 20 строк, входные данные экспорта, английский UI и мобильную вёрстку. Docker/живая MongoDB и реальные PostgreSQL/GitLab/Jira пользователя в этой среде не проверялись; тесты мокированного адаптера не равны интеграционному тесту живых сервисов.
